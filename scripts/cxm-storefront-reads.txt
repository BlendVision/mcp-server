# The operations data/api-index-cxm.json exposes: the CXM storefront subset, plus
# the org-unit listing, which is not CXM's but is what makes assigning to a
# department possible without carrying its roster through the agent.
#
# CXM (BlendVision's learning product) is not part of the published /bv
# contract: all 342 of its storefront operations are BV_INTERNAL. This file is
# the reviewed subset an agent may reach -- reads only, and only the ones a
# question about courses, content, spaces or assigned learning actually needs.
#
# Reads, plus two writes -- creating a program and creating a task -- listed
# because an agent that cannot see an operation cannot call it, and the AiSK
# router's "build me a course from these videos" and "assign it to Nick" flows
# need them. Being listed is not permission: `call_api` still refuses a
# mutating /cxm/ call unless that exact "METHOD path" appears in
# BLENDVISION_CXM_WRITES, so a deployment that sets nothing is read-only even
# with both writes indexed.
#
# The two are not equally safe, and the difference is worth stating rather than
# leaving for someone to discover. Creating a course can be undone by deleting
# it and nobody hears about it in between. Creating a task calls
# ScheduleNotificationsOnTaskCreated -- it mails the people it assigns -- so
# deleting the task afterwards does not unsend anything. An agent that assigns
# the wrong course to the wrong people has done something a person has to
# apologise for.
#
# It is here because assigning is half of what the product is for, and the
# earlier position -- index the create, refuse the assign -- left the agent able
# to build a course and unable to give it to anyone, which is not a safer
# product so much as an unfinished one. The per-deployment gate is where that
# judgement belongs: a deployment can index both and permit only
# `POST /cxm/storefront/v1alpha1/programs`, and several should.
#
# Nothing else that mutates belongs here. Still deliberately absent: PUT and
# DELETE on a program, updating or deleting a task, permission updates, and
# every licensed-content write. Changing or deleting something somebody else
# made is a different question from making one.
#
# Paths are matched exactly as "METHOD path", so the POST that creates a
# program is not pulled in by the GET that lists them.
#
# Rebuild after editing:
#   node scripts/build-api-index.mjs <internal-spec>.yaml \
#     -o data/api-index-cxm.json \
#     --actions <proto-dir>/bv \
#     --include @scripts/cxm-storefront-reads.txt

# --- Courses (programs) ---
# filter.author_name_keyword answers 「某講師的課程有哪些」 exactly (orbit!7889).
# The author is free text on the program row -- there is no instructor entity --
# so without it the question can only go to aisk/search, which matches
# semantically and returns courses that merely mention the name.
GET /cxm/storefront/v1alpha1/programs
GET /cxm/storefront/v1alpha1/programs/{id}
GET /cxm/storefront/v1alpha1/programs/{id}/overview
GET /cxm/storefront/v1alpha1/programs/{id}/arrangement

# --- Content ---
GET /cxm/storefront/v1alpha1/contents
POST /cxm/storefront/v1alpha1/contents:batch-get
POST /cxm/storefront/v1alpha1/contents:aggregate
GET /cxm/storefront/v1alpha1/licensed-contents

# --- Spaces (where content is organised) ---
GET /cxm/storefront/v1alpha1/spaces
GET /cxm/storefront/v1alpha1/spaces/{id}
GET /cxm/storefront/v1alpha1/spaces/{id}/contents
GET /cxm/storefront/v1alpha1/explore/me/outlines

# --- Assigned learning (tasks) ---
GET /cxm/storefront/v1alpha1/tasks
GET /cxm/storefront/v1alpha1/tasks/{id}
GET /cxm/storefront/v1alpha1/tasks:count-by-state
GET /cxm/storefront/v1alpha1/tasks/{id}:get-my-info
# The roster with a progress value per person. The task listing carries one
# overall figure, so "how far is each assignee" had no answer without this and
# was reported as something the platform does not keep.
GET /cxm/storefront/v1alpha1/tasks/{task_id}/assignees

# --- Who may see a course ---
# CreateProgram takes `permission.default_permission_role` as a whole
# PermissionRole -- id, name and access_role -- and orbit looks the role up BY
# ID, failing the create with "permission role mismatch: expected 1, got 0"
# when the id is empty. The id is a per-organisation row: only the organisation
# knows which one ACCESS_ROLE_CXM_VIEWER is, so it has to be read.
#
# A read, and the one this index was missing to make the write it already
# carries usable. Without it the AiSK agent had to scrape the row off an
# existing course's permission, which only finds a role some course already
# uses.
GET /cxm/storefront/v1alpha1/permissions/roles

# --- The asker's own learning record ---
GET /cxm/storefront/v1alpha1/analytics/my-activities/programs
GET /cxm/storefront/v1alpha1/analytics/my-activities/program-summaries
GET /cxm/storefront/v1alpha1/analytics/my-activities/content-summaries
# "what have I watched/read recently" -- one listing per content type, which is
# how the API splits them. Without these, a question about the asker's own
# viewing history has nothing to read.
GET /cxm/storefront/v1alpha1/analytics/my-activities/vods
GET /cxm/storefront/v1alpha1/analytics/my-activities/aods
GET /cxm/storefront/v1alpha1/analytics/my-activities/articles
GET /cxm/storefront/v1alpha1/analytics/my-activities/files
# "which courses am I part-way through" -- the only listing that answers it.
# Returns exactly the contents whose progress is between 1% and 99%, newest
# activity first; it is what the home page's Continue Watching row is built
# from. Everything else makes the agent choose between a listing that reports
# progress it never computed (ListPrograms writes 0 and NOT_STARTED into every
# row) and paging thousands of rows of /contents to find the few that moved --
# which is how one such question spent 260k tokens and then answered that the
# organization had no progress at all, while the asker's own screen showed 14%.
GET /cxm/storefront/v1alpha1/my-recently-viewed-contents
# 「最新課程有哪些」 -- and the ONLY listing that answers it. It is the endpoint
# the product's own pinned "最新課程" home line is built from (#582), so the
# ordering an answer gives matches the one the asker can see on their screen:
# available_since DESC, ties on the same calendar day by title ASC.
#
# It is here because the obvious alternative is wrong in a way nobody notices.
# ListPrograms is the CPM management listing: its filter is
# `exclude_permission_roles` and NOTHING else -- no visibility, no publish
# window -- so it returns drafts and in-review courses beside published ones,
# and sorting its rows by `updated_at` answers "recently edited", which puts a
# three-year-old course that got a typo fix today at the top. Asked
# 「最新課程有哪些」 that is exactly what came back.
#
# available_since is two-track and is NOT in the response: publish date for
# category-licensed contents, FIRST license start for single-content licenses
# (renewals never re-qualify a course). So the order has to be taken as given --
# it cannot be recomputed from what comes back.
#
# Phase 1 serves LICENSED (marketplace) content only; asking for SELF_CREATED
# is an explicit error rather than a quietly narrower answer, so an answer built
# on this has to say that self-produced courses are not in it.
GET /cxm/storefront/v1alpha1/my-latest-contents
# "which courses has anybody finished" -- counted from content_progress rows at
# 100%, grouped by course, across the whole organization. It touches no task
# table, so a course somebody finished on their own, unassigned and with no
# certificate, is counted here like any other. Without it the only completion
# figures reachable were the task rosters, and 「系統上完成的課程有哪些」 was
# answered as "self-directed completions are not tracked", which is false.
# Returns the TOP TEN by completion count and no more -- the limit is hardcoded
# server-side, so an answer built on it has to say so.
GET /cxm/storefront/v1alpha1/analytics/programs/top-completed
# "who finished it" -- names, where the listing above gives counts. Finished
# means progress at 100%, which is what the progress bar shows and what those
# counts are counted from. Ships with orbit!7889.
GET /cxm/storefront/v1alpha1/programs/{id}/completed-users
# Certification is a SEPARATE record: it exists only where a certificate was
# configured and is issued on its own criteria, so its holders are neither all
# of nor only the people who finished. Indexed for questions about
# certificates; answering "who completed this course" with it named three
# people for one course and nobody for eight others whose completion counts
# said otherwise.
GET /cxm/storefront/v1alpha1/programs/{id}/cert-users

# --- The one write (see the note at the top) ---
# Requires title, background, arrangement, permission, author_info, rating and
# level_info. Four of those cannot be defaulted and have to be asked for:
# the title, who may see it (permission.default_permission_role), the level,
# and which contents go in with what sequence.
POST /cxm/storefront/v1alpha1/programs

# --- The second write: assigning (see the note at the top) ---
# Requires name, start_time, end_time, at least one content, and people --
# `assignees`, an uploaded list, org units, or select-all. Sends mail to
# everyone it assigns, which is why it is the one entry here that a deployment
# should think about before naming it in BLENDVISION_CXM_WRITES.
POST /cxm/storefront/v1alpha1/tasks

# --- Assigning to a unit instead of to everyone in it ---
# CreateTask takes `assignee_org_units` -- one uuid per unit, expanded by the
# backend into every person it contains, unit heads and MATRIX members included.
# Without these two, "assign this to the marketing department" has to become a
# hundred `assignees` entries, which the agent cannot do: a roster of a hundred
# is 33,495 characters against its 30,000 result budget, and writing them back
# out is 4,456 output tokens against a 2,048 cap. It reads eighty people,
# believes it read all of them, and emits half a JSON array.
#
# One id instead. Both are BV_INTERNAL, so neither is in the public index, and
# `assignee_org_units` is unusable without the listing that turns 「行銷部」 into
# a uuid.
#
# ListOrgUnits is flat and carries each unit's `ancestors`, so two departments
# with the same name under different parents can be told apart -- which matters
# here more than anywhere: picking the wrong one assigns work to the wrong
# hundred people. With `keyword` set the scope is the whole organization and
# `parent_id` is ignored.
GET /bv/org/v1/organizations/org-units

# Answers "how many people would these units assign?" BEFORE the task is saved,
# and the org chart cannot answer it: its two head-count fields both exclude
# MATRIX assignments and neither counts unit heads, while assignment includes
# both. Nor can the caller add the per-unit numbers up -- picking a parent and
# its child, or two units sharing a matrix member, would count somebody twice.
# So the card can say how many people a confirmation would actually reach.
#
# A POST that reads: it declares ACTION_READ, and call_api decides by the
# declared action rather than by the method, so it is not gated as a write.
POST /cxm/storefront/v1alpha1/tasks/assignees:previewOrgUnits

# --- Semantic search over the same content ---
# The only way to answer "the newest courses" -- the programs listing has no
# sort parameter, while this takes sort=SEARCH_SORT_TYPE_UPDATED_AT_DESC and a
# filter.types of [SEARCH_SOURCE_TYPE_PROGRAM].
POST /cxm/storefront/v1alpha1/aisk/search
